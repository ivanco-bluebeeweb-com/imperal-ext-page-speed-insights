# Page Speed Insights — PREPARATION.md

**Статус:** planning (до кода)
**Владелец продукта:** vlad@bluebeeweb.com
**Дата подготовки:** 2026-08-11, v0.1
**Почему сейчас:** SEO Audit Engine уже мерит только грубый TTFB/elapsed_ms
(`SLOW_MS = 2500`, `VERY_SLOW_MS = 5000` в `seoaudit/rules.py`) — честно
помечен в коде как "не Core Web Vitals, а грубый сигнал". Реальные Core Web
Vitals (LCP, CLS, INP) не измеряются нигде в портфеле, хотя это официальный
ranking-фактор Google и то, что реально спрашивают агентские клиенты
("почему сайт медленный"). Это следующий логичный слой SEO-пайплайна после
технического аудита контента/индексируемости.

---

## 1. Паспорт приложения

**Page Speed Insights** — приложение-коннектор к Google PageSpeed Insights
API v5 (Lighthouse + CrUX). По домену/URL получает реальные Core Web Vitals
(LCP, CLS, INP, TTFB), Lighthouse-скоры (Performance/Accessibility/
Best Practices/SEO) и список конкретных "opportunities" (что чинить), и
сохраняет их как историю по сайту — чтобы видеть тренд, а не разовый снимок.

Работает и как самостоятельный инструмент ("проверь скорость g4s.md"), и
как **слой данных для SEO Audit Engine** — тот уже посылает находки по
слоям (`LAYER_TECHNICAL` и т.д.), но про реальную скорость страницы у
живых пользователей ничего не знает.

## 2. Проблема в человеческих словах

Когда **владелец агентского сайта или SEO-специалист** сталкивается с
**падением позиций или жалобой клиента "сайт тормозит"**, ему приходится
**вручную открывать pagespeed.web.dev по одному URL за раз, копировать
цифры в таблицу, и повторять это раз в месяц вручную**, из-за чего
**регресс скорости после обновления темы/плагина замечается через недели,
а не сразу, и нет истории, чтобы показать клиенту прогресс**.

Существующий SEO Audit Engine эту боль не закрывает: он даёт грубый сигнал
"ответ сервера медленный" по TTFB, но не настоящие Core Web Vitals, которые
Google реально использует для ранжирования и которые видит PageSpeed
Insights у web.dev.

## 3. Пользовательский путь (UX-карта, до кода)

**Основной путь:**
1. Пользователь называет сайт(ы) — "проверь скорость climtec.md" или это
   вызывается автоматически из SEO Audit Engine / по расписанию.
2. Приложение запускает `runPagespeed` для мобильной и десктопной стратегии
   (обе — Google их разделяет, и мобильная почти всегда хуже).
3. Возвращает: три Lighthouse-скора (0-100), LCP/CLS/INP из **полевых
   данных** (CrUX, реальные пользователи) если они есть для сайта, иначе
   честно помечает "нет полевых данных, только лабораторный прогон".
4. Сохраняет снимок с датой — история, а не разовый факт.
5. При повторном прогоне — показывает разницу с прошлым разом (по аналогии
   с `compare_audits` у SEO Audit Engine): что улучшилось, что просело.

**Missing/error путь:** URL не резолвится, сайт лежит, PageSpeed API вернул
ошибку (429 rate limit, 500 undocumented throttling — оба задокументированы
у Google) — честный отказ с кодом ошибки, не выдуманный "скор 0".

**Blocked путь:** нет API-ключа Google — понятная инструкция, куда его взять
(console.cloud.google.com, включить "PageSpeed Insights API", создать
API key — сам API можно дергать и без ключа, но тогда общий лимит на
все анонимные вызовы намного жёстче и его нельзя увеличить).

**Recovery путь:** rate limit (429/500) — backoff и понятное сообщение
"Google ограничил частоту проверок, попробую через N секунд", не тихий сбой.

**Точка, где решение остаётся за человеком:** сама оптимизация (сжать
картинку, убрать render-blocking JS) — это либо ручная работа разработчика,
либо явно отдельная задача в SEO Audit Engine `tasks`/трекере. Приложение
диагностирует и советует, не трогает сайт.

## 4. Ценность и метрики

- Время до обнаружения регресса скорости: с недель → до суток (если в
  портфельном расписании) или до секунд (по запросу).
- Число сайтов с историей Core Web Vitals за последние 90 дней (не разовый
  снимок).
- Доля находок SEO Audit Engine слоя TECHNICAL, подкреплённых настоящими
  Core Web Vitals, а не только грубым TTFB.
- Неуспех/нет спроса: если пользователи продолжают спрашивать про скорость
  через pagespeed.web.dev вручную, а не через это приложение — значит
  интеграция в чат/пайплайн не сработала.

## 5. Границы: делает / не делает (P0)

**Делает (P0):**
- Запускает PageSpeed Insights API v5 (`runPagespeed`) для одного URL,
  strategy=mobile и desktop, category=PERFORMANCE (+ опционально
  ACCESSIBILITY/BEST_PRACTICES/SEO/PWA).
- Извлекает и сохраняет: Lighthouse-скоры по категориям, полевые метрики
  (LCP/CLS/INP/TTFB percentile+category из `loadingExperience`/
  `originLoadingExperience`), лабораторные метрики, топ-N "opportunities"
  (audits с `score < 0.9` и реальной экономией времени).
- История снимков по сайту/странице + сравнение "было/стало".
- BYOK: пользователь даёт свой Google API key (свой квотный бюджет,
  25,000 запросов/день по умолчанию — не общий лимит Imperal).
- IPC-функция `check_site_speed_ipc`, которую **вызывают другие
  приложения** (SEO Audit Engine, Content Strategy Hub) — не только чат.
- Ежедневное/еженедельное расписание по сайтам из Sites Registry.

**Не делает (P0):**
- Не оптимизирует сайт сама (не сжимает картинки, не меняет код,
  не трогает WordPress) — это отдельный, ручной или через wordpress-hub
  шаг, с подтверждением человека.
- Не заменяет SEO Audit Engine — дополняет его слоем реальных Core Web
  Vitals, не дублирует контент/индексируемость проверки.
- Не хранит и не анализирует данные конечных пользователей сайта —
  CrUX-данные уже агрегированы и анонимны на стороне Google, это просто
  проценты по бакетам (good/needs improvement/poor).
- Не гарантирует SLA по скорости ответа Google API (документированы и
  429, и недокументированные 500 throttling — забюджетировано retry, не
  обещание мгновенного результата).

**Рискованные действия, запрещённые в P0:** любая автоматическая правка
сайта по результатам замера. Даже "давай я включу сжатие картинок" — нет,
это предложение человеку, не автономное действие.

## 6. Данные, конфиденциальность, интеграции

**Данные:** URL сайта/страницы (уже публичный, не персональный), сырой
JSON-ответ Lighthouse (может быть большим — 500KB-2MB на прогон), извлечённые
метрики и скоры, timestamp. Никаких персональных данных посетителей сайта —
CrUX отдаёт только агрегированные проценты.

**Retention:** хранить снимки истории (не одноразово), но не бесконечно
сырой Lighthouse JSON — держать сырой ответ N дней (например 30) для
разбора конкретной находки, а агрегированные метрики (скоры, LCP/CLS/INP)
— бессрочно как история тренда, это дёшево по объёму.

**Tenant isolation:** API-ключ — секрет уровня user (`scope: "user"`), как
у Trello/Media Studio — свой ключ, свой квотный бюджет, никогда не шарится
между пользователями.

**Интеграции — честный статус:**

| Интеграция | Статус | Что именно |
|---|---|---|
| Google PageSpeed Insights API v5 | **available** | публичный REST API, ключ через Google Cloud Console |
| Sites Registry (`list_sites` IPC) | **available** | тот же паттерн, что уже использует Content Strategy Hub/WordPress Hub — читает список сайтов, не пишет |
| SEO Audit Engine | **available**, интеграция P0 | добавить IPC-вызов из SEO Audit Engine → Page Speed Insights при аудите слоя TECHNICAL, и/или наоборот — Page Speed Insights пушит находку "критично медленный LCP" как доп. finding |
| Content Strategy Hub | **not needed for P0** | возможное будущее: учитывать скорость при `run_content_audit`, не блокирует P0 |
| WordPress Hub | **not needed for P0** | автопочинка (сжатие картинок и т.п.) — вне периметра P0, требует отдельного решения владельца как write-действие на чужом сайте |

**Правило соблюдено:** недоступные/будущие интеграции не входят в основной
demo-flow P0 — только Google API + Sites Registry обязательны.

## 7. Интеграция в общий SEO-пайплайн (главный вопрос из задачи)

Сегодняшний пайплайн: `Sites Registry` (что за сайты) → `SEO Audit Engine`
(контент/индексируемость/структура/технический слой, грубый TTFB) →
`Content Strategy Hub` (что писать дальше) → `Article Writer` → `Media
Studio` (картинки) → `WordPress Hub` (публикация).

Page Speed Insights встраивается как **дополнительный источник находок
для слоя TECHNICAL** в SEO Audit Engine, по той же модели, что уже
работает у Content Strategy Hub с Sites Registry (`SITE_PROVIDER_APP_IDS`
список app_id, которые эту функцию реализуют) — то есть:

1. **Page Speed Insights экспонирует** `@ext.expose`-метод
   `check_site_speed_ipc(url, strategy) -> {scores, field_metrics,
   lab_metrics, top_opportunities}` — прямой in-process IPC, без чата,
   так же как `ctx.extensions.call("wordpress-hub", "list_connected_sites")`
   у Content Strategy Hub.
2. **SEO Audit Engine узнаёт о нём** — во время аудита слоя TECHNICAL
   вызывает этот IPC (если приложение установлено — best-effort, деградирует
   тихо, если не установлено или ключа нет, ровно как Sites Registry-паттерн
   "transient IPC error degrades gracefully instead of hard-failing").
   Результат превращается в `Finding` с `layer=LAYER_TECHNICAL`, реальными
   LCP/CLS/INP вместо/в дополнение к грубому `elapsed_ms`.
3. **Другие приложения могут спросить сами** — например, если пользователь
   в чате Content Strategy Hub спросит "а как у нас со скоростью", Webbee
   вызовет Page Speed Insights напрямую как отдельное приложение (chat-функция),
   не обязательно через SEO Audit Engine.
4. **Обратная связь не нужна** — Page Speed Insights не должен знать о
   существовании SEO Audit Engine (однонаправленная зависимость, как и
   везде в этом репо: "SITE_PROVIDER_APP_IDS" — потребитель знает про
   поставщика, не наоборот).

Это значит: чтобы SEO Audit Engine и Content Strategy Hub "знали" про новое
приложение, нужно **одной строкой добавить его app_id** в соответствующий
реестр (как `SITE_PROVIDER_APP_IDS` в `content-strategy-app/main.py`), а
не переписывать их логику.

## 8. P0 — минимальный законченный путь

**Главный use case:** "Проверь скорость climtec.md" → пользователь получает
реальные Core Web Vitals (mobile+desktop), Lighthouse-скор, топ-3
opportunities, и это сохраняется в историю.

**Сущности:**
- `PageSpeedSnapshot` — один прогон: site, url, strategy, timestamp,
  scores (performance/accessibility/best-practices/seo), field_metrics
  (lcp/cls/inp percentile+category, если есть), lab_metrics, raw_audits_ref.
- `Opportunity` — одна находка внутри снимка: audit_id, title,
  potential_savings_ms, score.

**Инструменты P0 (chat + IPC):**
1. `check_site_speed` (chat) — запустить проверку 1 URL, mobile+desktop.
2. `list_speed_history` (chat) — история снимков по сайту.
3. `compare_speed_snapshots` (chat) — разница между двумя прогонами (как
   `compare_audits` у SEO Audit Engine).
4. `list_opportunities` (chat) — топ находок последнего снимка.
5. `check_site_speed_ipc` (`@ext.expose`) — то же самое для других
   приложений, без чата.
6. Расписание (`@ext.schedule`) — еженедельный автопрогон по сайтам из
   Sites Registry, best-effort уведомление о регрессе (по аналогии с
   ночным SEO-аудитом: не "вот 40 метрик", а "что просело").

**Server-side safety gates:**
- Backoff на 429/500 (задокументировано у Google: 429 = честный rate limit
  с `Retry-After`, 500 = недокументированный per-origin throttling, ждать
  60-180 сек) — не долбить API молча.
- Структурные коды ошибок (по образцу `codes.py` в SEO Audit Engine) —
  `PSI_NO_API_KEY`, `PSI_RATE_LIMITED`, `PSI_URL_UNREACHABLE`,
  `PSI_NO_FIELD_DATA` (не ошибка, а честное "низкий трафик — нет CrUX").
- Не выдавать выдуманный скор, если Google вернул частичный/ошибочный ответ
  — та же дисциплина, что "аудит не судит то, чего не видел" у SEO Audit
  Engine.

**Явно исключено из P0:** PWA-категория (редко нужна агентским сайтам),
множественные устройства кроме mobile/desktop-Lighthouse-профиля,
автоматическая починка находок.

**Acceptance criteria (простыми словами):** пользователь называет домен →
через секунды получает реальные цифры LCP/CLS/INP + Lighthouse-скор для
мобильной и десктопной версии, с понятной интерпретацией "хорошо/нормально/
плохо" — не сырой JSON.

## 9. Технический контракт (проверено по докам, не выдумано)

- Эндпоинт: `GET https://www.googleapis.com/pagespeedonline/v5/runPagespeed`
- Параметры: `url` (обяз.), `key` (API-ключ), `strategy` (MOBILE/DESKTOP),
  `category` (можно несколько: PERFORMANCE, ACCESSIBILITY, BEST_PRACTICES,
  SEO, PWA), `locale`.
- Ответ: `lighthouseResult` (лабораторные данные, всегда есть) +
  `loadingExperience`/`originLoadingExperience` (полевые CrUX-данные,
  **может отсутствовать** для сайтов с низким трафиком — это нормальное
  состояние, не ошибка).
- Квоты по умолчанию (Google Cloud): **25,000 запросов/день**,
  **400 запросов/100 сек** (~4/сек) — с собственным API-ключом. Без ключа
  общий анонимный лимит намного жёстче и не масштабируется — поэтому ключ
  обязателен для регулярного использования в портфеле.
- Ошибки: **429** — задокументированный rate limit с заголовком
  `Retry-After`. **500** — недокументированный per-origin throttling при
  устойчивой нагрузке, требует выжидания 60-180 сек перед повтором.

## 10. Секреты (BYOK, по образцу Media Studio/Trello)

- `pagespeed_api_key` — Google API key с включённым PageSpeed Insights API,
  `scope: "user"`, `write_mode: "both"`, обязательный. Инструкция в
  описании: console.cloud.google.com → APIs & Services → включить
  "PageSpeed Insights API" → Credentials → Create API key.

## 11. UI/панели — обязательное соответствие `UI_INTERFACE_STANDARD.md`

Проверено ПЕРЕД кодом, по правилу файла (сверка обязательна при
проектировании панелей нового приложения, не постфактум).

**Ровно одна кнопка "App settings"** (secondary) в сайдбар-слоте
приложения. Клик рендерит настройки в **центральном слоте** (не модалка,
не отдельный таб) — тем же механизмом переключения панели, что уже
используют другие приложения репозитория (`ui.Call("__panel__<id>", ...)`,
как у date-строк в DataForSEO Connector).

**Что обязано быть на экране настроек этого приложения** (не только
подключение ключа — весь настраиваемый периметр P0):

| Настройка | Тип | Где хранится |
|---|---|---|
| Google API key (`pagespeed_api_key`) | секрет, connect/disconnect | `ctx.secrets` |
| Расписание автопроверки (вкл/выкл, дни, час, какие сайты) | значения формы | store, по образцу `schedule_settings.py` у SEO Audit Engine |
| Пороги "критично" для авто-уведомления | **официальные Google-пороги по умолчанию** (LCP>4s / CLS>0.25 / INP>500ms), но поле должно существовать в настройках, а не быть зашито в код без возможности увидеть/подтвердить | store |
| Категории Lighthouse для прогона (Performance всегда вкл; Accessibility/Best&nbsp;Practices/SEO/PWA — переключатели) | чекбоксы | store |
| Retention сырого Lighthouse JSON (дней) | число, дефолт 30 | store |
| Notify mode (все прогоны / только регрессии / выкл) | select, по аналогии с `notify_mode` у Automations | store |

**Сохранение и обратная связь** (правило 4-6 стандарта):
- Каждое поле реально сохраняется через свой `chat.function`/handler
  (`save_schedule_settings`, `save_alert_thresholds`,
  `save_category_toggles`, `save_retention_days`, `save_notify_mode`,
  `connect_pagespeed_key` / `disconnect_pagespeed_key`), не просто меняет
  локальный UI-стейт.
- Каждый handler возвращает `ActionResult.success(data=..., summary=
  "понятный текст успеха")` → зелёное оповещение внизу экрана; при ошибке —
  `ActionResult.error(error="человеческая причина", ...)`, тот же канал,
  статус "ошибка".
- `refresh_panels` указывается явно там, где известно, какой слот менять
  (например, сохранение ключа обновляет и центр, и сайдбар — там может
  быть индикатор "подключено"); если неочевидно — не передавать, SDK
  обновит все панели сама.

**Чек-лист перед сдачей UI** (копия из стандарта, отмечать по факту
реализации, не заранее):
- [ ] Ровно одна кнопка "App settings" в сайдбаре.
- [ ] Клик рендерит настройки в центральном слоте.
- [ ] Экран содержит все 6 настроек из таблицы выше, не только ключ.
- [ ] Каждое поле реально сохраняется write-вызовом.
- [ ] Зелёное оповещение об успехе с понятным текстом.
- [ ] Оповещение о неудаче с понятной причиной (не сырой код/трейс).
- [ ] Нужные слоты обновляются автоматически после сохранения.

## 12. Открытые вопросы для владельца (не блокируют P0, но нужно решение)

1. Порог "критичная деградация" для авто-уведомления по расписанию — брать
   Google-пороги CWV (LCP >4s / CLS >0.25 / INP >500ms = "poor") или свои?
   → Предлагаю: использовать официальные Google-пороги, не изобретать свои.
2. Нужно ли слать найденные проблемы сразу как `AuditTask` в SEO Audit
   Engine трекер задач, или это отдельный список — до первой реальной
   интеграции решить не критично, можно начать с отдельного списка и
   добавить связь второй итерацией.
3. Часть D-аналог (не для P0): автоматическая генерация правки (например,
   "добавить `loading=lazy` на картинку") и отправка её в WordPress Hub —
   это write-действие на чужом сайте, требует отдельного явного решения
   владельца, как non-goals в VBS. Записано, не реализуется без отдельного да.
